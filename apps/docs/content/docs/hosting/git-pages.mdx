---
title: Git and Pages hosting
description: Publish skills from a Git repository to a static host.
---

Your skills can live in a Git repository and be published by its deployment pipeline. The CLI builds a checked-out copy of that repository; GitHub Pages, GitLab Pages, or another static host serves the result. Agents read those hosted files, not the Git repository itself.

<Steps>
<Step>

## Build from the repository

The CLI runs from the local checkout's root—the directory containing `skills/` and any `remote-skills.json`. On your machine, that means opening a terminal in the repository. In CI, it means running the build after the checkout and dependency-install steps.

With the [CLI installed](/docs/quickstart#serve-it) in that checkout:

<Tabs items={["npm", "pnpm", "bun"]} groupId="package-manager" persist>
<Tab>

```bash
npm exec -- remote-skills build
```

</Tab>
<Tab>

```bash
pnpm exec remote-skills build
```

</Tab>
<Tab>

```bash
bun run remote-skills build
```

</Tab>
</Tabs>

`build` validates the skills and creates `dist/`. The source, lockfile, and publisher settings in Git give the pipeline the same inputs as your local build. The CLI does not clone a repository URL or accept a separate project-directory argument.

</Step>
<Step>

## Serve the output

Your provider's deployment step uploads the contents of `dist/`, including `.well-known`. The [hosting guide](/docs/hosting/archive-to-origin) covers response types and preserving the built files unchanged.

Discovery expects `.well-known` at the hostname's root. A custom domain such as `skills.example.com` gives a Pages project that layout without changing the source repository.

A default project site such as `https://example.github.io/repository-name/` puts the files one level deeper. It needs a custom domain or hosting configuration that serves them at the host root instead—an **origin-root** mapping. Adding `/repository-name/` to the SDK URL does not change where it looks for the catalog.

</Step>
<Step>

## Check the deployed result

From a machine that can reach the deployed hostname, run:

<Tabs items={["npm", "pnpm", "bun"]} groupId="package-manager" persist>
<Tab>

```bash
npm exec -- remote-skills verify https://skills.example.com
```

</Tab>
<Tab>

```bash
pnpm exec remote-skills verify https://skills.example.com
```

</Tab>
<Tab>

```bash
bun run remote-skills verify https://skills.example.com
```

</Tab>
</Tabs>

Once verification succeeds, the SDK can connect to `https://skills.example.com`. Future source changes follow the same checkout, build, and deployment process.

</Step>
</Steps>

## Updates and rollback

To keep older releases available alongside an update, the build needs the previous output as an input. [Versions and history](/docs/versions) shows how to carry those releases forward; without that input, a build contains only the skills in the current checkout.

To roll back, redeploy a previous complete catalog and its artifacts. Existing sessions keep their selected bytes; later sessions discover the restored catalog.
